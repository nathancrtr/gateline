Specification: log rotator

Context

The log rotator is a long-running daemon responsible for compressing and archiving application log files. It currently operates on a fixed 24-hour rotation window, which is insufficient for high-throughput services that can generate hundreds of megabytes of logs per hour. This specification defines a size-triggered rotation policy with configurable thresholds and retention windows.

The existing implementation uses a single-threaded gzip pipeline that blocks the main event loop during compression of large files. This becomes a bottleneck when multiple log streams exceed their size threshold simultaneously.

Requirements

R1 — Size-triggered rotation

  • ◻ AC1.1 — When a log file exceeds its configured max_size_bytes threshold, the rotator initiates a compression pass within 30 seconds of the threshold being crossed.
  • ◻ AC1.2 — The original log file is replaced with a symlink to the compressed archive, preserving existing tail -f readers.
  • ◻ AC1.3 — Rotation events emit a structured JSON log line to the system journal containing: file path, original size, compressed size, start time, and duration.

R2 — Concurrent compression

  • ◻ AC2.1 — The rotator spawns compression workers in a thread pool sized to min(os.cpu_count(), max_workers). A sample input of 50 log files across 8 cores completes all compressions within 120 seconds.
  • ◻ AC2.2 — Worker panics are caught at the pool boundary and logged without bringing down the main rotator process.
  • ◻ AC2.3 — A --dry-run flag outputs which files would be rotated without modifying the filesystem.

Assumptions

ASSUMPTION: The filesystem supports atomic symlink creation. If the deployment target uses a filesystem without symlink support (e.g., certain FUSE mounts), the rotator falls back to a copy-and-rename strategy with a corresponding warning.

ASSUMPTION: Log files are written exclusively by a single writer process. Concurrent writes during compression are out of scope for this version.

Data model

The rotator configuration is read from a YAML file at /etc/log-rotator/config.yaml with the following structure:

# log-rotator configuration
source: /var/log/app
patterns:
  - "*.log"
  - "access*.log"
max_size_bytes: 104857600  # 100 MB
retention_days: 30
max_workers: 4
compression: zstd

Compression performance characteristics

Algorithm Ratio Speed Memory
gzip 6.2:1 baseline ~8 MB
zstd 8.1:1 2.3× faster ~12 MB
lz4 4.5:1 5.1× faster ~4 MB

Zstd at compression level 3 offers the best trade-off for our workload: 2.3× the throughput of gzip with 30% better compression. Memory overhead of 12 MB per worker is acceptable given our 512 MB per-container budget.

Out of scope

  • Remote log shipping (handled by a separate log-shipper service)
  • Encryption-at-rest for compressed archives
  • Automatic cleanup of archives older than the retention window (deferred to v2)
  • Integration with log aggregation platforms (Datadog, Splunk)
